### A2 — Client hardening (graduate `client.py`) ✅ done (2026-08-25)
- [x] Rate-limit throttle: per-installation hourly budget **and** the 900 pts/min secondary limit,
      100-concurrent cap; back off on secondary limits (`tenacity`); per-run budget log line.
      Implemented as `_InstallationThrottle` (one per `installation_id`, since limits are
      installation-scoped): a token-bucket for the 900 pts/min secondary budget shared by REST
      and GraphQL, a `threading.BoundedSemaphore(100)` for the concurrent cap, and
      `record_hourly()`/`GitHubClient.budget_snapshot()` for the measured (never estimated)
      primary budget -- from REST's `X-RateLimit-*` response headers and GraphQL's `rateLimit`
      field. `cli_probe` logs one `rate_limit_budget` line per run via `budget_snapshot()`.
      Secondary-limit backoff (`_SecondaryRateLimited`, a 403/429 carrying `Retry-After`) is
      wired into the existing `tenacity` retry via a custom `wait` callable that sleeps for
      exactly the duration GitHub names, falling back to the prior exponential schedule for
      plain 5xx/network failures.
- [x] ETag / `If-None-Match` conditional requests on the REST gap-fill path (304s are free).
      `rest_get` caches the `ETag` response header per `(installation_id, path, params)` and
      replays it as `If-None-Match` on the next call to the same resource.
- [x] GraphQL query documents as `.graphql` files; **every query requests
      `rateLimit { cost remaining nodeCount resetAt }`** and feeds the throttle (measure, not estimate).
      `src/server/ingest/git/graphql/probe.graphql` (the POC's inline query, graduated) plus
      `client.load_graphql(name)`, which refuses to load a document missing `rateLimit` --
      caught at load time rather than as a silently-wrong budget later. `GitHubClient.graphql()`
      reads `data.rateLimit` when present and corrects the throttle's placeholder spend to the
      measured cost.
- **Tests** (`tests/server/ingest/git/test_client_hardening.py`, 15 new + the 9 kept POC tests
  = 23 total): JWT claims (kept); token re-mints exactly once across expiry; a 401 (both on
  `installation_token` and `rest_get`) raises `GitHubInstallationUnauthorized` and makes
  exactly one HTTP call, never looping; a 403/429-with-`Retry-After` backs off then succeeds,
  not fails (`respx`); ETag replay produces a `304`; the `.graphql` loader rejects a document
  missing `rateLimit`; the throttle's token-bucket and hourly-exhaustion wait behave correctly
  in isolation. Added `respx` as a test-only dependency (`requirements.txt`). Full suite: 1537
  passed, the same 1 pre-existing unrelated failure as after A1.

### A4 — Mapper (build `map_github.py` + `worker/git_map.py`) ✅ done (2026-08-25)
- [x] `src/server/ingest/git/map_github.py`: pure payload → artifacts per §5.3/§5.4 — `pr`, `review`,
      review/conversation-comment counters, `push`→`commit` (≤2048; >2048 records the range),
      `check_suite`, installation lifecycle. Grouping keys; `is_bot`; revert + `reverts_sha`.
      `org_id` is an INPUT (the worker resolves it via `git_installations`, since a pure function
      can't); `MapResult.mapped=False` is the first-class unmapped outcome. Fields the module often
      can't know from one event (`files`, `commit_shas`, `before_sha`/`after_sha`/
      `integration_method`, `user_id`) are emitted `None` rather than guessed.
- [x] **Merge-transition capture (§5.7):** `merge_commit_sha` from the merged `pull_request`;
      `integration_method` inferred from the correlating push's own commit list (single new commit
      == squash; newest commit's "Merge pull request" message == merge; otherwise == rebase --
      documented in `_infer_integration_method` as a v1 webhook-only approximation, since the real
      signal is the merge commit's parent count, which no webhook payload carries); `commit_shas`
      from the push's commit list. **Correlates in both arrival orders**, since neither delivery is
      guaranteed to land second: the push's transition data is stashed in `info["github.push_meta"]`
      on its head commit artifact at mapping time, and the worker checks both directions
      (`correlate_push_into_pr` when the push lands, `apply_push_meta_to_pr` when the merged PR
      lands and finds the commit already there via `get_commit_info_by_sha`).
- [x] `src/server/worker/git_map.py`: the `git_map` topic handler — claim (`claim_delivery`, A1),
      read delivery, map, upsert artifacts/repos/installations, correlate, mark `done`/`unmapped`,
      **one transaction** (`dispatch.py`'s SAVEPOINT, same as `rollup`). Registered in
      `config/worker.yaml`'s `topics` and wired into `cli_work.py`'s handler table.
- [x] Prune `done`/`unmapped` deliveries past retention: `prune_git_deliveries`, a `git_prune`
      timer in `cli_work.py` (new `WorkerConfig.git_deliveries_retention_days`/`git_prune_interval_s`).
      TODO marker in `map_github.py` on the unmapped `issues`/`issue_comment` paths (v1.5).
- [x] **A real bug the A1 schema/queries didn't anticipate, found and fixed while building this:**
      `upsert_artifact`'s blind `EXCLUDED.x` overwrite would have let an ordinary later
      `pull_request` webhook (e.g. `synchronize`) silently erase `stats.review_count`/
      `comment_count` (accumulators only `bump_artifact_stat` maintains), a correlated
      `merge_commit_sha`/`before_sha`/`after_sha`/`integration_method`/`commit_shas`, a backfilled
      `files` list, or a resolved `user_id` -- because the mapper, being a pure function of ONE
      event, genuinely doesn't know those values most of the time and would emit `None`/defaults
      for them. Fixed: `stats` now merges (`||`) instead of replacing; the sticky scalar/list
      columns now `COALESCE(EXCLUDED.x, git_artifacts.x)` so a `None` from the mapper preserves
      whatever a different pass already established, with `COALESCE(:x, '[]'/'{}')` at INSERT time
      keeping the NOT NULL jsonb columns satisfied on a brand-new row. Covered by
      `test_review_bump_survives_a_later_pull_request_resync`.
- **Tests** (`tests/server/ingest/git/test_map_github.py` — 26 pure-mapper tests including 8

### A5 — Backfill / gap-fill readers (build `backfill.py`; evolve `cli_probe`→`cli_backfill`) ✅ done (2026-08-25)
- [x] GraphQL **bulk reader** (`GraphQLBackfillReader`, `graphql/backfill_search.graphql`): PRs
      with files/reviews/commits in one round trip, via GitHub's `search` API (`repo:o/n is:pr
      updated:>=X sort:updated-asc`) rather than `repository.pullRequests` -- only `search`
      supports server-side date filtering, which is what lets a resumed run start past its
      cursor instead of paging a whole repo's history every time. REST **gap-fill/fallback**
      reader (`RestBackfillReader`): an ETag-conditional (A2) newest-first list pass that stops
      at the cursor, plus a per-PR detail+files+commits+reviews pass. Both produce the identical
      `MapResult` artifact shape the webhook mapper does and are applied through the same write
      path (new `apply.py`, extracted from `worker/git_map.py` so the webhook-triggered handler
      and both backfill readers share one apply function -- exactly "one mapper, three readers,
      cannot drift," §8.2, now enforced by the code structure rather than just documented).
      **The REST reader reuses `map_github.map_delivery` directly** for a PR's core fields (a
      REST PR-detail response has the same shape as a webhook's `pull_request` object) and only
      augments it with what REST's separate endpoints add; the GraphQL reader's wire shape is
      structurally different, so it shares the same lower-level helpers instead
      (`_artifact_id`, `_is_bot`, `_parse_reverts_sha`, `_parse_linked_issue`,
      `_infer_integration_method`) -- two independent paths converging on the same fields, which
      is what the reader-agreement test actually exercises.
- [x] Per-repo cursor on `git_repos.backfill_cursor`/`backfill_state`: new `get_repo_cursor`
      (`FOR UPDATE`, so a manual `cli_backfill` and the gap-fill timer over the same repo
      serialize) and `advance_repo_cursor` (`GREATEST`-guarded, so a page can never walk the
      checkpoint backwards) queries in `git.yaml`. `GapFillRunner.tick()` sweeps every known
      repo (`git_repos`) via the REST reader, restricted to "updated since cursor" -- the
      **primary** delivery-loss recovery path (§10: GitHub's own redelivery reaches only 3 days
      back; a persisted timestamp cursor has no such limit), registered as a worker `Timer`
      (`git_gapfill_enabled`/`git_gapfill_interval_s` in `config/worker.yaml`, gated on
      `config/github.yaml` being present the same way the pricing table degrades).
- [x] `cli_backfill.py` (`--repo`/`--org`, `--since`, `--reader graphql|rest`, `--list-only`,
      `--dump`) + `utils/git_backfill.sh`.
- **Tests** (`tests/server/ingest/git/test_backfill.py` — 4 respx-mocked reader tests;
      `test_backfill_db.py` — 2 real-Postgres integration tests): GraphQL paging across two
      responses; a non-empty `errors[]` propagates as `GitHubApiError` and the reader never
      returns partial data (enforced by the client itself, A2 — this proves the reader doesn't
      accidentally swallow it); the REST list pass stopping at the cursor;
      **reader-agreement — a GraphQL-backfilled and a REST-backfilled artifact for one PR are
      byte-identical**, built from two independently-constructed fixtures (one GraphQL-shaped,
      one REST-shaped) representing the same PR; cursor resume mid-run maps each PR exactly once
      even when a resumed run re-issues an overlapping page; a backfill sweep landing over an
      already-webhook-mapped PR leaves the core identity/state fields byte-identical while
      correctly adding what only backfill can supply (commit count, review artifacts) --
      enrichment, not corruption. Rate-limit backoff on these readers is A2's throttle,
      unmodified: both readers call `GitHubClient.rest_get`/`graphql` directly, with no bypass,
      so no separate backoff test was needed here.
      **Known v1 gap, documented in `backfill.py`'s module docstring:** `before_sha`/`after_sha`
      (§5.7) are `None` on a backfilled PR -- they come only from the base-branch push a live
      webhook sees at merge time, which a bulk historic read has no way to observe. The
      `upsert_artifact` COALESCE (A4) means a later live webhook can still fill them in without
      a backfill re-run losing anything.
      Full suite: 1585 passed, same 1 pre-existing unrelated failure as after A1–A4.

      1. **State-carrying setup callback** (`GET config.setup_path`, added to `routes.py`
         alongside the webhook route): GitHub's redirect carries `installation_id` (spoofable,
         per §6.1's own caveat) and our signed `state` (`state_token.py` — HMAC-signed,
         self-contained, no server-side session needed until the redirect actually arrives).
         Binds a **pending** org only (new table `git_pending_installs`, migration
         `2e4db06ce3e2`) — never writes `git_installations` directly from an unverified
         redirect; only the signed `installation.created` webhook or a reconcile pass adopts it
         for real. `resolve_org_id` (`worker/git_map.py`) checks-and-consumes the pending
         binding the first time ANY delivery for that installation is mapped, so it applies
         regardless of whether the webhook or a reconcile gets there first.
      2. **Login-match** — explicitly **not built**: it needs an "org's registered GitHub org
         login" to compare against, and no such registry exists in this codebase (storage.md
         §3.6 lists `orgs` as **DEFERRED** — "designed when org-level rollups... land"). Building
         a comparison with nothing on the other side of it would be inert; revisit alongside the
         `orgs` table.
      3. **Operator mapping** (`cli_installations map --installation ID --org-id ORG`) +
         **default org** fallback (`DEFAULT_ORG_ID = "default"`, already in `git_map.py` since
         A4) — both working today.

      the same PR. **Run twice** with fresh delivery ids per run (the honest simulation of two
      independent deliveries describing the same GitHub event, stronger than replaying one
      literal delivery id) — and it found two real bugs on the first attempt, both fixed:
      1. **`review_count` double-counted on a second pass.** It was a delta accumulator
         (`bump_artifact_stat`, A4) with no memory of what it had already counted, so replaying
         the same `pull_request_review` event doubled it — silently violating git-source.md
         §10's "re-running a delivery changes nothing," specifically the documented
         mapper-defect recovery path ("fix the mapper, re-run over `git_deliveries`"). Fixed by
         no longer accumulating it at all: `review_count` is now **recomputed from the actual
         review rows** (`recompute_review_count`) every time a webhook-mapped review lands,
         since every review already gets its own idempotently-upserted artifact row — COUNT(*)
         over real rows can't double-count no matter how many times it is replayed. Skipped when
         a PR ships in the same batch (backfill), which already knows `review_count` from the
         API's own authoritative `totalCount`. `comment_count` (which has no per-comment
         artifact row to count) keeps the delta-bump shape but gained a dedup set
         (`info.github.counted_comments`, keyed `"<comment_id>:<action>"`) so a replayed comment
         event is now a no-op too, not a second count.
      2. **`commit_shas`/`files` silently reset to `[]` on a later "unknown" write.** A real bug
         in `upsert_artifact` itself (A1/A4), not the mapper: the UPDATE branch's
         `COALESCE(EXCLUDED.commit_shas, git_artifacts.commit_shas)` never actually preserved
         anything, because `EXCLUDED.commit_shas` mirrors the INSERT branch's OWN
         `COALESCE(:commit_shas, '[]')` — so it is never really NULL, and the "preserve on
         unknown" COALESCE always picked the wrongly-defaulted `EXCLUDED` value instead of the
         existing row. Concretely: a push-correlated PR's `commit_shas` got wiped back to `[]`
         the next time an ordinary `pull_request` webhook (which doesn't know commit shas)
         re-mapped it. Fixed by having the UPDATE branch reference the **raw bind parameter**
         (`:commit_shas`/`:files`) directly instead of `EXCLUDED`, since the same named
         parameter carries its original (possibly-NULL) value independent of what the INSERT
         branch derived from it. This is exactly the class of bug an isolated per-query test
         cannot see (each of A1's and A4's own tests passed) but a full-pipeline,
         same-artifact-touched-twice test catches directly.
- [x] Extended `docs/manual-testing.md` §6: `cli_backfill` as probe 4 (§6f) plus what "passing"
