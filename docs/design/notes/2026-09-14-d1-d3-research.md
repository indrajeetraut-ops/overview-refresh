# Research — Track benchmark distributions (D3) & Track lifecycle + context curve (D1)

**Date:** 2026-09-14
**Feeds:** `docs/plan/2026-09-12-mvp-gap-closure-plan.md` → "Track benchmark distributions"
and "Track lifecycle & context curve".
**Status:** research only — no code changed. This grounds both tracks in what data actually
exists (code *and* the live stack DB) before either gets its own mini-plan.

Method: read every TODO site + the aggregate/fold/query layer behind it, then checked the
running stack DB (`talium_stack_pg`, `econ`, 82 sessions / 1 connected repo) to see whether
the real data can actually feed each feature.

TL;DR of the surprises:
1. **D1-context-curve is not "L".** The per-turn context-size series it wants is *already
   assembled* inside `carry_of` (`graph_fold.py:705`) and then thrown away except for its last
   value. The work is "persist the series," not "build a new fold."
2. **A single upstream bug blocks the data half of BOTH tracks.** `session_git_links` is
   **empty** on the live stack (0 rows), so every PR cost resolves to `$0` and no session is
   joined to its PR. D3's cost distributions and D1-lifecycle's session→PR span both starve on
   this. **Root cause (diagnosed): a query-path bug**, not missing data — the `session_commit_shas`
   correlator query reads the wrong event_type/path; commit shas are captured and a corrected
   query links 19/82 sessions. See the cross-cutting section + T0 in the plan.
3. **Merged-PR volume is adequate for a repo-wide distribution, but per-feature is degenerate**
   — most features are single-PR, so the current per-feature envelope is a one-point
   "distribution." This is the real justification for `D3-envelope-scope`.

## Track benchmark distributions (D3)

TODO sites: `manager/service.py:931` (`D3-envelope-scope`), `:934` (`D3-benchmark`);
schema `schemas/manager.py:704,722` (`benchmark: None = None`); FE already has the cold-start

### D3-envelope-scope — widen the cost-to-finish envelope from feature-only to repo-wide

**Today:** `feature_detail` builds the envelope from *this feature's own* member-PR costs:
```
envelope = forecast.cost_per_pr_envelope(list(pr_costs.values()))   # service.py:993
```
With 18 of the repo's features being single-PR, that input list is usually length 1 → the
"envelope" is a single point (`cost_per_pr_envelope` returns min==p25==median==max). That is
the statistical weakness the TODO names, confirmed against real data.

**What's already available** — this is a *query swap*, not new machinery:
- `repo_merged_prs_in_range` (`manager.yaml:254`) already returns every merged PR for a repo.
- `pr_costs_for_ids` (`manager.yaml:70`) already costs a PR-id list.
- `forecast.cost_per_pr_envelope` (`forecast.py:29`) already produces the p25/median/p75/p90/p99
  shape the UI reads.

So the change is: cost the *repo's* trailing merged PRs (not just the feature's members) and
feed that to `cost_per_pr_envelope`; keep `feature_cost_to_finish(open_prs, envelope)` as-is.
Feature detail already resolves its repo (`f.ref.project_key` → `git_repo_id`), so the repo
scope is in hand. **Decision needed:** the trailing *window* (e.g. last 90 days vs all-time)
and whether to fall back to feature-local when the repo itself is below a volume floor.

**Size:** S–M (was implied L). The only real work is a new "repo-wide merged-PR costs" fetch
+ the window decision.

### D3-benchmark — cost/time percentile of this feature vs peer features

**Today:** `"benchmark": None` hardcoded (`service.py:1011`), schema pins `benchmark: None`.
FE renders `UnavailableNote` "a cross-feature cost/time distribution" (`FeatureScreen.tsx:166`).

**What's already available:** `quality.list_features_for_repo` (`quality.py:116`) enumerates
*every* feature in a repo, each `_feature_view` already carrying `spend.usd_micros` and
`merged_prs`. That is exactly the population a cross-feature distribution needs. A benchmark
block = { this feature's spend/time, the repo's feature-spend distribution, the resulting
percentile }. `forecast.percentile`/`dist_stats` already compute the stats.

Two axes the mockup implies ("vs similar features", cost **and** time):
- **cost axis:** `spend.usd_micros` per feature — available now.
- **time axis:** feature lead time = `last_merged_at − first_session_started_at`. Both
  timestamps are already computed in `feature_detail`'s `lifecycle` block (`service.py:986`),
  but `list_features_for_repo` doesn't currently return them per-feature — a small extension to
  `_feature_view`, or compute lead time in the benchmark aggregate directly.

**Decision needed:** what "similar" means. Cheapest first cut = all features in the same repo
(no similarity model). A tighter cut (by size / label / issue-type) is a later refinement and
shouldn't gate the first version.

**Size:** M. New `aggregate` over `list_features_for_repo`'s output + a `FeatureBenchmark`
schema to replace the `benchmark: None` pin.

### The blocker both D3 halves share

`pr_costs_for_ids` and the feature member-cost path both derive PR cost by joining
`session_git_links → session_info.cost_effective_usd_micros`. On the live stack that link
table is **empty**, so *every* merged PR costs `$0` (verified: 23 merged PRs, 0 with cost).
A repo-wide envelope or a cross-feature distribution built today would be a distribution of
zeros. The aggregate code is not the problem — **the `session_commit_shas` correlator query
reads the wrong event path** (diagnosed; despite `pr_classification` having 25 rows, the sha
join finds nothing because it looks at `tool_call`/`payload.commit.sha` instead of the real
`tool_result`/`payload.raw.toolUseResult.gitOperation.commit.sha`). Fixing that query (T0)
populates links and non-zero costs — no re-ingest. See the cross-cutting section.

## Track lifecycle & context curve (D1)

### D1-lifecycle — build session lifecycle spans from `session_git_links` + PR events

**What the endpoint has today:** `_session_economics_block` (`single_user/service.py:850`)
reads only `session_info` — it never joins the session to its PR, so it can only show the
session's own start→last-activity, which `SessionScreen` already draws. Real build/review/
rework spans need the PR side.

**What's now available (code side):** the PR timeline data the plan's original churn/reopen
track said "isn't persisted" now largely *is*:
- `git_artifact_events` (`storage/schema/git.py:128`, working tree) — append-only
  opened/reopened/closed/merged transitions with `occurred_at`. **Caveat: uncommitted +
  unmigrated** — table absent on the live stack, so this feeds nothing until it ships and
  backfills.
- `pr_review_children` (`manager.yaml:100`) — per-review state + submitted_at → first-review
  time, review rounds.
- `git_artifacts` (PR row) — `created_at`/`merged_at`/`closed_at`.
- `session_git_links` (`manager.yaml:72` shape) — the session→PR edge.

So a session lifecycle span series is assemblable: session `started_at` → linked PR
`created_at` (build) → first review submitted (review) → merged/closed (ship), with reopen
loops from `git_artifact_events`. `feature_detail` already does a coarse repo/feature version
of exactly this (`service.py:986`); D1 is the same idea scoped to one session's linked PR(s).

**Blocker:** `session_git_links` is empty on the stack (same T0 query-path bug as D3, fixed
there — not a separate problem). No link → no PR to hang spans on. And reviews are thin here
(2 rows), so even with links the review span would often be absent (honest `None`, not wrong —
but worth knowing before promising a rich timeline).

**Size:** M for the join + span assembly (was L). The "L" premium was for building PR-timeline
capture, which the churn/reopen work already did — D1-lifecycle now mostly *consumes* it. The
dependency is data population, not new capture code.

### D1-context-curve — persist a per-turn context-size series (the cheap surprise)

**Plan's framing:** "needs a persisted per-turn context-size series that nothing folds today …
L". The first half is right (nothing *persists* it); the second is not — the series is already
*computed*.

**Finding:** `carry_of` (`graph_fold.py:582`) already builds, at line 705:
```python
contexts = [(n.ts, (n.attrs.get("cache_read_tokens") or 0)
                 + (n.attrs.get("cache_write_tokens") or 0))
            for n in assistants]        # sorted by ts
```
i.e. per-assistant-request **context size = cache_read + cache_write** — the fold's own
documented definition of "per-request context" (`graph_fold.py:694` comment). It uses this to
find cache-reload gaps, then discards everything except `contexts[-1]` (persisted as
`carry.projected.context_tokens`). The whole curve is right there and dropped.

`turns_of` (`graph_fold.py:295`) independently gives the per-turn frame (index, started/ended,
tokens) the curve's x-axis wants. Joining the two — or emitting `contexts` bucketed by turn —
yields `context_curve = [{turn/index, context_tokens, ts}, …]`.

**Work:** add a `context_curve` output to the fold (write it in `info_of`, `graph_fold.py:957`,
alongside `segments`/`practices`), promote it in `_session_economics_block` (drop the
`None`/`UnavailableNote`), and render it (the SessionScreen slot already exists). No new
extraction, no new graph traversal beyond what `carry_of` already does.

**Backfill:** unlike title/reasoning-token fixes, this needs **no re-ingest**. All 82 sessions
have their graph persisted in `session_graph`; a backfill script loads the graph, re-runs the
`contexts` derivation, and merge-patches `info["context_curve"]` — same backfill pattern the
segment-pricing note describes for `channel_cost`/`carry`.

**Open question (decision):** downsample policy for long sessions (the 80+-turn sessions) — cap
points, or bucket per-turn? Recommend per-turn (cheap, ≤~90 points even at the top of the
observed distribution; no need to downsample at this scale).

**Size:** S–M (was L). This is the highest-leverage, lowest-cost item across both tracks and a
good first thing to land.

## Cross-cutting blocker — `session_git_links` is empty on the live stack

Three of the four deliverables (D3-envelope-scope, D3-benchmark cost axis, D1-lifecycle) depend
on `session_git_links`, and it has **0 rows** on the running stack even though `pr_classification`
has 25.

**Diagnosis complete (corrected 2026-09-14).** An earlier draft of this note guessed "0 sessions
captured a commit sha → capture gap." That was wrong — it repeated the broken query's own path.
Commit shas ARE captured (25 sessions, 123 `gitOperation` events). The real cause is a query-path
bug: a git commit is stored as a **`tool_result`** event with the sha at
`payload.raw.toolUseResult.gitOperation.commit.sha` (abbrev 7-char, e.g. `f1817e7`), but
`session_commit_shas` (`config/queries/pr_class.yaml:42`, and siblings at `:99`/`:133`) reads
`event_type='tool_call'` + `payload.commit.sha` — a shape the normalizer never emits. The query's
cited extractor `claude_code.py::_git_commit_from_result` does not exist (comment-only). Fix =
correct the query path + keep the prefix match (PR shas are full 40-char); no re-ingest, the data
is already in `signal_blob`. **Verified: the corrected sha-prefix join links 19/82 sessions.**
Branch-match is NOT needed as the primary mechanism (it would only address the squash/rebase
sha-rewrite residual). See T0 in the implementation plan.

D1-context-curve is the one deliverable that does **not** touch `session_git_links` — it's pure
fold-over-graph — which is another reason to land it first while the link-population question is
being chased.

Also note: `git_artifact_events` (D1-lifecycle's reopen/transition source) is uncommitted in the
working tree and absent from the stack DB. D1-lifecycle can't be validated end-to-end until that
schema ships and backfills too.

## Revised sizes & suggested order (vs the plan)

| Item | Plan size | Revised | Why |
|---|---|---|---|
| D1-context-curve | L | **S–M** | series already computed in `carry_of`; backfillable from `session_graph`, no re-ingest |
| D1-lifecycle | L | **M** | PR-timeline capture already done by churn/reopen track; this consumes it |

| D3-benchmark | M | **M** | `list_features_for_repo` is the ready-made population; needs a "similar" decision |

**Suggested order:**
1. **D1-context-curve first** — cheapest, highest-leverage, and the only item not gated on the
   `session_git_links` blocker.
2. **Diagnose/fix `session_git_links` population** (upstream; unblocks the rest).
3. **D3-envelope-scope**, then **D3-benchmark** (benchmark reuses the repo-wide fetch).
4. **D1-lifecycle** last of the four — also needs `git_artifact_events` shipped + migrated.
